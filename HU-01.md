# HU-01 — Reducir la exposición del token de autenticación

## Origen

- **Componente:** web
- **ID:** H-WEB-01
- **Hallazgo:** Token de sesión en `localStorage`; permanece disponible para JavaScript del mismo origen aunque token y usuario ahora se guarden en `sessionStorage`.
- **Estado en HALLAZGOS.md:** Pendiente.
- **Evidencia:** `web/src/app/services/session.service.ts:27-57`; `web/src/app/login/login.component.ts:59`; `web/src/app/dashboard/dashboard.component.ts:79`.

## Contexto

El frontend centraliza la sesión en `SessionService` y usa `sessionStorage`, que reduce la persistencia tras cerrar la pestaña, pero sigue siendo accesible para JavaScript del mismo origen. El hallazgo no afirma que haya ocurrido una explotación; identifica que la mitigación actual no evita el acceso al token desde ese JavaScript.

## Ajustes necesarios

- Definir con los responsables de backend y frontend una forma de mantener la sesión que no exponga el token a JavaScript del navegador.
- Evaluar un mecanismo de sesión gestionado por el servidor, como una cookie `HttpOnly`, con sus controles de transporte y protección contra solicitudes no deseadas. La solución requiere acordar cambios compatibles en los servicios que autentican y consumen las tareas.
- Actualizar `SessionService` y las solicitudes del frontend para usar el mecanismo acordado, retirar el almacenamiento del token en `localStorage` y `sessionStorage`, y conservar el flujo funcional de login, consulta de tareas y cierre de sesión.
- No considerar `sessionStorage` por sí solo como resolución del hallazgo. No introducir tokens, secretos ni credenciales en el código del frontend.

## Criterios de aceptación

- Una prueba automatizada de sesión confirma que, después de autenticarse, no hay token de autenticación en `localStorage` ni en `sessionStorage`.
- Una prueba de integración verifica que una sesión válida permite consultar tareas y que una sesión ausente o inválida no autoriza la consulta.
- Una prueba del flujo confirma que el login permite llegar al dashboard y que cerrar sesión invalida o elimina la sesión según el mecanismo acordado; una consulta posterior no conserva autorización.
- Si se acuerda una cookie de sesión, una prueba o inspección automatizada confirma el atributo `HttpOnly` y los atributos de transporte acordados para el entorno.
- El cambio conserva el contrato funcional acordado para login y consulta de tareas, verificado por pruebas de regresión.

## Evidencia esperada

- Decisión documentada sobre el mecanismo de sesión y sus responsabilidades entre frontend y backend.
- Pruebas automatizadas de almacenamiento, autenticación, consulta de tareas y logout con resultados reales.
- Evidencia de que el token no está disponible en almacenamiento accesible a JavaScript; si se usa cookie, registro de los atributos configurados sin incluir valores sensibles.
- Resultado de las pruebas de regresión del flujo y referencias actualizadas a los archivos modificados.
